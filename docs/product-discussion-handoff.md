# 跨境业务场景运营系统

## 冷启动交接文档

> 用途：在新的会话中恢复本项目的产品背景、已经确认的方向、Demo 范围和后续工作方式。新会话应先阅读本文件和 `README.md`，再开始修改产品或代码。

## 1. 项目背景

项目发起人同时负责产品工作，需要把一套面向外贸、跨境业务和外贸综合服务的平台做成可演示、可讨论、可继续开发的产品 Demo。

目标不只是做几个孤立的页面，而是让技术团队能够从 Demo 和文档中理解：

- 有哪些业务场景。
- 每个场景服务谁、解决什么问题。
- 用户从哪里进入，看到什么，完成什么操作。
- 场景处理过程中有哪些状态、确认点、异常和下一步动作。
- 场景结果如何写回长期存在的业务数据。
- 前端、后端、测试可以据此开始拆分和实现，不再强依赖一份只描述页面的 PRD。
- 同一套产品既可以用于项目解决方案交付，也可以独立运营。

参考方向：

- [Flyelep](https://www.flyelep.cn/)
- LinkFox

## 2. 产品定位

本产品是一个面向外贸及跨境业务的**业务场景运营系统**。

产品以商品、企业、客户、线索、询价、报价、合规案件、订单、履约、库存和服务商等业务对象为基础，将多个业务场景组织成可执行、可追踪、可沉淀的工作流程。

它支持：

- 企业自己使用。
- 平台运营方为多个企业提供服务。
- 各地政府或政府背景公司的外贸综合平台运营。
- 按地区、行业、项目、组织配置不同的场景组合。
- Web 端和微信小程序协同处理同一批业务数据。

## 3. 最重要的产品表达原则

### 3.1 场景优先，不以技术名词做产品结构

用户侧不突出“Agent”“AI”“模型”“Agent 管理”等概念，也不把技术组件当作主导航。

产品应围绕用户要完成的事情来表达，例如：

- 商品经营。
- 客户与线索。
- 合规处理。
- 询价与报价。
- 订单与履约。
- 服务商协同。
- 经营分析。

技术实现中可以存在智能处理、规则、检索、外部接口和异步任务，但这些是底层实现，不是用户理解产品的入口。

### 3.2 不是“输入后输出一个文档”

场景结果不能停留在一次性报告或文件。场景必须操作真实的业务对象，并将用户确认后的结果写回业务数据。

例如：

- 商品处理结果写回商品数据库、商品版本、素材库、渠道内容和发布任务。
- 客户画像写回客户档案，并关联线索、触达记录和商机。
- 合规诊断生成合规案件、风险项、材料清单、整改任务和复核记录。
- 报价处理形成报价版本，并能继续转为商机、询价或订单。
- 订单处理更新订单、履约节点、库存、风险事件和异常任务。

### 3.3 候选结果与正式数据分离

处理结果先作为候选结果保存，用户确认、修改或驳回后，才写回正式业务数据。

```text
选择场景
→ 选择或创建业务对象
→ 输入或上传材料
→ 处理
→ 查看候选结果
→ 确认、修改或驳回
→ 写回正式业务数据
→ 生成任务、通知或下一步业务动作
```

每次写回要保留版本、来源、操作者、时间和审计记录。候选结果必须绑定生成时的源版本，源数据已经变化时不能直接覆盖当前正式数据。

### 3.4 两类交互方式

场景根据复杂度选择交互形式，但底层规则统一：

- 短、单一、低认知负担的处理，使用连续向导。
- 跨对象、跨角色、需要持续跟进的处理，使用业务工作台。

两类页面都必须共享同一套场景记录、状态、任务、确认、写回、失败恢复和审计规则，不能在页面里各自维护一套逻辑。

### 3.5 主线优先，支线后置

讨论和实现都要先抓住主线：

1. 用户是谁。
2. 他要完成什么业务目标。
3. 进入哪个场景。
4. 操作哪个业务对象。
5. 如何确认结果并继续下一步。

权限细节、字段级校验、外部接口、技术选型和复杂边界属于支线。只有在影响主流程、数据一致性、权限或实现决策时才提前展开。不要在主线尚未稳定时陷入细节。

## 4. 用户类型与端侧分工

当前确认的主要用户有四类。

### 4.1 线下批发档口业主

主要诉求：

- 快速制作商品图片和场景图。
- 快速制作短视频或营销素材。
- 低成本完成商品展示、内容发布和客户沟通。

更适合：

- 微信小程序快速拍照、上传、处理和查看结果。
- Web 端进行批量管理、素材整理、商品维护和后续复用。

### 4.2 跨境电商卖家

主要诉求：

- 商品图片、场景图、视频和营销内容。
- 商品标题、描述、翻译、类目和海关编码优化。
- 海外合规、商品风险和经营诊断。
- 全球获客、客户画像、邮件触达和线索跟进。

更适合：

- Web 端作为主工作台，处理商品、渠道版本、合规、获客和经营数据。
- 微信小程序用于拍摄上传、快速查看、审批确认、任务提醒和移动跟进。

### 4.3 B2B 跨境运营公司

这里的 B2B 运营公司指从事 B2B 跨境业务，不是以开网店为核心的卖家。

主要诉求：

- 全球海关数据和采购商数据获客。
- 采购商画像构建。
- 相似客户扩量。
- 线索筛选、分配、触达、跟进和商机转化。
- 询价、报价、服务商协同和订单履约。

更适合：

- Web 端作为获客、线索和业务协同主工作台。
- 微信小程序用于线索提醒、移动跟进、客户沟通记录和关键结果确认。

### 4.4 平台运营方

平台运营方包括各地政府的公司或政府背景公司，负责外贸综合平台的运营，为多个企业提供物流、通关、报税等服务，并覆盖 9810、9710、1039 等外贸业务模式。

主要诉求：

- 多租户企业、服务商和项目管理。
- 为不同项目配置场景组合。
- 物流、通关、报税等综合服务协同。
- 企业入驻和路径引导。
- 服务需求识别、服务商匹配、报价排序和服务商评级。
- 订单、履约、风险、库存和数据报告的统一运营。

更适合：

- Web 端作为平台运营、组织管理、项目配置、服务商管理、数据分析和业务监管主工作台。
- 微信小程序作为企业、服务商和平台人员的移动入口，用于提交需求、上传材料、查看进度、处理任务和确认结果。

### 4.5 端侧结论

当前采用 **PC 端 + H5 端** 的策略（按发起人最新要求，替代原“Web 为主、微信小程序为辅”）。

- **H5 端**面向线下批发档口业主：手机管理自己的商品（拍照上新、编辑信息、内容生成与确认、合规处理、发布任务），低门槛、移动采集、快速处理。
- **PC 端**面向企业运营与平台运营：复杂业务工作台、批量操作、数据管理、配置与经营分析。

两个端不各自复制业务逻辑，而是共享同一套业务对象、场景处理记录、任务和状态。

### 5.3 场景目录的组织方式

不把 54 个场景都做成 54 个独立复杂流程。采用“全量目录 + 重点闭环”的方式：

- 场景目录展示全部场景，支持按项目、业务域、用户和关键词筛选。
- 每个场景遵循统一定义模板。
- 重点场景做完整可交互流程。
- 其他场景先展示进入条件、输入、处理步骤、确认点、写回对象、异常恢复和下一步动作。
- 项目来源、接口对象等技术元数据保留在技术说明中，但不作为用户侧主导航。

## 6. 统一场景定义模板

每个场景至少要明确以下内容，技术可直接据此拆分前后端和测试：

1. 场景名称：用户能理解的业务名称。
2. 业务目标：解决什么业务问题。
3. 适用用户：哪类角色使用。
4. 适用项目：温州、南京、通用产品或外部对接。
5. 进入入口：Web、微信小程序或两端。
6. 目标业务对象：处理商品、线索、案件、报价、订单等什么对象。
7. 前置条件：必须存在什么数据、权限或材料。
8. 输入材料：表单、图片、视频、文件、文本、数据记录或外部结果。
9. 处理步骤：用户可见的业务步骤。
10. 候选结果：处理后展示给用户确认的内容。
11. 确认点：哪些信息必须人工确认，哪些可以自动写回。
12. 正式写回：写入哪些业务表、版本、关系或任务。
13. 任务与通知：写回后生成什么待办、提醒或下一步动作。
14. 异常恢复：文件失败、外部接口失败、超时、规则无法判断、部分成功如何处理。
15. 权限边界：谁可查看、编辑、确认、驳回或复核。
16. 审计要求：保留谁在什么时间以什么来源做了什么操作。
17. 下一步动作：继续触达、报价、整改、入库、发货或分析等。

## 7. 底层业务对象与数据底座

### 7.1 核心对象

系统不应把页面当作数据边界。建议围绕以下长期对象设计数据库和接口：

- 组织、企业、平台项目、用户、角色、项目成员。
- 商品、SKU、商品属性、商品素材、商品版本、渠道商品版本。
- 客户企业、联系人、客户关系、供应商关系、服务商关系。
- 线索、客户画像、跟进记录、触达任务、商机。
- 询价、匹配结果、服务需求、物流报价、正式报价、报价版本。
- 合规案件、风险项、整改任务、合规材料、复核记录。
- 订单、履约单、履约节点、风险事件、库存、入库记录。
- 报告、数据任务、规则配置、数据质量记录。
- 场景定义、场景运行记录、候选结果、任务、通知、文件、版本记录、审计日志、外部集成记录。

### 7.2 对象关系原则

```text
组织/项目
  → 用户与权限
  → 商品与商品版本
  → 客户、供应商、服务商
  → 线索与客户画像
  → 询价与报价
  → 合规案件与整改任务
  → 订单与履约
  → 库存与入库
  → 报告与数据质量
```

场景运行记录是处理过程的记录，不替代业务对象；候选结果是待确认的临时版本，不替代正式版本；任务是推动业务继续向前的工作单，不替代对象状态。

### 7.3 版本与并发

- 商品、报价、合规材料等可变对象要有版本号。
- 候选结果保存 `sourceVersion`。
- 确认时检查源版本是否仍是当前版本。
- 版本不一致时提示用户比较、合并或重新处理，不允许静默覆盖。
- 每次正式写回与审计记录应在同一事务边界内完成。

### 7.4 状态与任务

每个对象都要区分：

- 对象自身生命周期状态。
- 场景处理状态。
- 聚合进度。
- 待确认任务状态。
- 异常和重试状态。

不要把“内容处理中”“渠道发布中”等处理进度直接塞进商品主生命周期状态；这些应由商品版本、素材任务、渠道发布记录或场景运行记录表达。

## 8. 重点 Demo 闭环

当前 Demo 已实现或演示以下重点路径。

### 8.1 商品经营

这是完整的跨端演示：

1. 微信小程序创建商品草稿或上传素材。
2. Web 端进入商品工作台。
3. 完善商品基本信息、素材、描述、标签和渠道版本。
4. 处理产生候选结果。
5. 用户确认、修改或驳回。
6. 结果写回商品数据库和商品版本。
7. 生成后续任务，例如渠道发布或补充信息。
8. 微信小程序读取更新后的商品状态和结果。

### 8.2 线索经营

1. 进入全球线索或采购商数据场景。
2. 查看线索列表和采购商画像。
3. 筛选、确认和分配线索。
4. 生成跟进任务。
5. 记录触达结果。
6. 形成客户关系或商机。

### 8.3 合规处理

1. 选择境内或境外合规处理方向。
2. 创建合规案件并上传商品、报关或企业材料。
3. 查看识别出的风险项和依据。
4. 确认风险并生成整改任务。
5. 匹配服务商或指定处理人。
6. 提交整改材料。
7. 复核并关闭或重新打开案件。

### 8.4 询价与报价

1. 创建或接收询价。
2. 解析询价需求并匹配相似商品或服务。
3. 形成服务清单和物流报价候选。
4. 调整数量、价格、币种、有效期和服务条款。
5. 生成报价版本。
6. 发送、查看客户反馈并继续转商机或订单。

### 8.5 订单与履约

1. 从报价或业务需求进入订单。
2. 查看订单全生命周期和履约节点。
3. 分发供应商或服务商。
4. 更新备货、通关、物流、交付等节点。
5. 识别风险并生成异常任务。
6. 处理库存、入库和补货协同。
7. 完成订单或保留异常记录。

## 9. 平台运营模式

系统需要支持平台多租户和企业独立运营两种模式：

```text
平台运营方
├── 企业 1
├── 企业 2
├── 服务商
└── 项目
```

基本原则：

- 数据默认按组织隔离。
- 企业拥有自己的工作区、用户和业务数据。
- 平台运营方可以管理多个企业、服务商和项目。
- 项目可以配置允许使用的场景、流程和服务商范围。
- 项目成员关系决定访问范围。
- 跨组织协作只开放必要的对象和字段。
- 服务商可以处理被分配的服务任务，但不能越权确认企业正式业务数据。

平台运营侧应重点演示：

- 企业入驻与路径引导。
- 项目和场景配置。
- 服务商管理与评级。
- 服务需求分发。
- 跨企业运营数据和风险概览。
- 9810、9710、1039 等模式下的服务流程承载能力。

## 10. 产品架构表达

产品架构不以 Agent 列表作为中心，而应表达四层关系：

```text
用户与入口层
  Web 工作台 / 微信小程序 / 平台运营端 / 企业与服务商入口

场景与工作流层
  商品经营 / 客户与线索 / 合规处理 / 询价与报价 / 订单与履约 /
  服务市场 / 经营分析

业务对象层
  商品 / 企业 / 客户 / 线索 / 询价 / 报价 / 合规案件 /
  订单 / 履约 / 库存 / 服务商 / 报告

平台底座层
  组织权限 / 文件与素材 / 任务通知 / 版本审计 /
  数据接入 / 规则与处理服务 / 外部系统连接 / 运行监控
```

产品架构图回答“用户如何从业务目标进入场景，并操作哪些业务对象”。

## 11. 系统架构表达

系统架构图回答“前端、后端、数据和外部系统如何支撑这些场景”。建议保持以下逻辑：

```text
Web / 微信小程序
        ↓
统一身份、组织、项目与权限
        ↓
场景编排与业务流程服务
        ↓
商品、客户、线索、合规、询价、报价、订单、履约、服务市场服务
        ↓
业务数据库 / 文件素材存储 / 搜索与数据分析 / 任务与通知
        ↓
外部数据源、物流、通关、报税、渠道和第三方服务
```

实现时要明确：

- 同一场景不能因 Web 和小程序不同而产生两套后端规则。
- 外部系统失败不能破坏已保存的业务对象和处理记录。
- 长耗时处理要异步化并可查看进度、失败原因和重试入口。
- 外部接口要有适配层，不能让页面直接依赖供应商接口字段。
- 关键写回、权限校验和审计必须由后端负责，前端不能作为可信边界。

## 13. 当前 Demo 与生产系统的边界

当前 Demo 使用确定性的示例数据和本地持久化，重点验证产品结构、交互、状态和对象关系，不代表已经完成生产接入。

后续生产化需要替换或补充：

- 真实业务数据库和迁移脚本。
- 真实身份、组织、项目和权限服务。
- 真实文件和素材存储。
- 真实异步任务队列、通知和重试机制。
- 外部海关、采购商、物流、通关、报税和渠道数据适配器。
- 真实处理服务、规则配置和版本管理。
- API 契约、接口幂等、错误码和审计查询。
- 接口测试、集成测试、端到端测试和权限测试。

第一阶段不要求实现所有外部系统，也不要求把每个场景都做成独立复杂页面。应优先保证核心对象、状态流转和闭环可扩展。

## 14. 下一阶段建议顺序

按主线推进，不要一开始同时铺开 54 个场景：

1. 固化核心业务对象和生命周期状态。
2. 把本地 Store 的接口整理成可替换的 Repository/API 边界。
3. 以商品经营为第一个真实后端闭环，打通 Web 与微信小程序共享数据。
4. 以线索经营、合规处理、询价报价、订单履约各选一条主流程做接口化。
5. 建立统一任务、通知、文件、版本、审计和异常重试底座。
6. 再逐批补齐场景目录中其余场景的正式工作流。
7. 最后接入平台运营、多租户、服务商和外部业务系统。

## 15. 新会话工作规则

新会话接手时请遵循：

- 先阅读本文件、`README.md` 和 `docs/superpowers/specs/2026-08-27-cross-border-scenario-platform-design.md`。
- 先判断需求属于产品主线、实现主线还是支线细节。
- 如果可以合理假设，不要反复向发起人询问已确认的内容。
- 如果发现需求会改变产品主线或带来明显数据、权限、架构风险，先暂停并说明取舍。
- 不要把产品改造成 Agent 管理台或模型管理台。
- 不要把场景改成只生成报告的单次操作。
- 不要为 PC 端和 H5 端复制两套业务逻辑。
- 不要绕过业务对象、版本、任务、审计和权限直接在页面里写死结果。
- 修改代码后必须运行与改动相关的测试，并在完成前运行构建和类型检查。
