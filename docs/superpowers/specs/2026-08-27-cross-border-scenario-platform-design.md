# 跨境业务场景运营系统设计

## 1. 结论

本产品是一个面向外贸及跨境业务的场景化运营平台。它以商品、企业、客户、线索、询价、报价、合规案件、订单、履约和服务商等业务对象为基础，把业务场景组织成可执行、可追踪、可沉淀的工作流程，并支持按地区、行业或项目组合成不同解决方案。

产品不以技术能力、处理模型或自动化组件作为用户侧产品结构。用户从业务问题进入场景，处理真实业务对象，确认结果后写回业务数据，并继续下一步业务动作。

## 2. 目标与范围

### 2.1 目标

- 让前端知道每类用户从哪里进入、看到什么、完成什么操作。
- 让后端知道业务对象、状态、处理记录、写回规则和对象之间的关系。
- 让测试知道主流程、状态转换、确认点、失败恢复和权限边界。
- 用一个统一底座承载不同地区、行业和项目的场景组合。
- 使同一套能力既可以由平台运营方交付给多个企业，也可以由单个企业独立运营。

### 2.2 第一阶段交付

- 高保真可交互 Web 原型。
- 微信小程序关键页面预览和跨端流程演示。
- 产品架构图。
- 系统技术架构图。
- 全量场景目录和统一场景定义模板。
- 五条完整业务闭环的交互说明。
- 核心业务对象、状态、数据写回和任务规则说明。

第一阶段使用示例数据和模拟处理，但必须表现出提交、处理中、候选结果、确认、写回、任务生成、异常和历史记录。

### 2.3 第二阶段交付方向

- 真实业务数据库。
- 真实前后端接口。
- 核心对象和状态流转。
- 文件与素材存储。
- 异步处理、通知和失败重试。
- 测试数据、接口测试和核心流程测试。

外部数据源、渠道发布和复杂自动化处理可以先使用适配接口与模拟服务，不阻塞核心业务闭环。

### 2.4 非目标

- 第一阶段不建设所有场景的独立复杂页面。
- 第一阶段不实现生产级外部系统接入。
- 第一阶段不建设独立的技术能力管理后台。
- 第一阶段不把每个场景包装成一个独立产品。
- 第一阶段不实现复杂的多人实时协同编辑。

## 3. 已确认的产品原则

### 3.1 场景优先

用户首先看到“我要做什么”，而不是技术名词或系统组件。

```text
选择业务场景
→ 选择或创建业务对象
→ 输入或上传材料
→ 处理
→ 查看候选结果
→ 确认、修改或驳回
→ 写回正式业务数据
→ 产生任务或下一步动作
```

### 3.2 业务对象优先

场景不是孤立页面，也不是一次性输出。场景通过处理记录操作长期存在的业务对象。

例如，商品内容制作必须写回商品素材库和商品版本；客户画像必须写回客户档案；合规诊断必须生成合规案件、风险项和整改任务；报价必须形成报价版本并能够继续转商机或订单。

### 3.3 候选结果与正式数据分离

场景产生的结果先保存为候选结果。用户确认后才写回正式业务数据，且保留版本和操作记录。

```text
候选结果
→ 用户确认或修改
→ 正式业务版本
```

无需人工确认的低风险处理可以配置为自动写回，但必须保留日志、版本和追溯入口。

### 3.4 两种交互方式，共享同一套业务规则

- 简单、单一、短流程场景使用连续向导。
- 复杂、跨对象、跨角色、需要持续跟踪的场景使用业务工作台。
- 两种方式共享同一套场景处理记录、状态、任务、确认、写回和日志规则。

### 3.5 产品语言

用户可见内容使用业务语言：商品经营、客户与线索、合规处理、询价与报价、订单与履约等。技术实现说明可以描述异步处理、规则、检索、外部接口和自动化服务，但这些不作为用户侧导航和核心产品概念。

## 4. 用户、组织与权限

### 4.1 组织模式

系统支持平台多租户和企业独立运营两种模式。

```text
平台运营方
├── 企业 1
├── 企业 2
├── 服务商
└── 项目
```

- 平台运营方可以管理多个企业、服务商和项目。
- 企业拥有自己的工作区、用户和业务数据。
- 企业可以独立使用，也可以参加一个或多个平台项目。
- 数据默认按组织隔离。
- 项目授权、角色权限和跨组织协作决定数据是否可见或可编辑。

### 4.2 主要角色

- 企业负责人：查看企业业务数据，确认关键结果，分配任务。
- 商品运营人员：处理商品、素材、内容、渠道版本和发布任务。
- 获客或销售人员：筛选线索、维护客户、触达和跟进。
- 合规人员：受理案件、处理风险、管理材料、整改和复核。
- 供应链或履约人员：管理订单、履约节点、库存、物流和异常。
- 服务商：查看被分配的服务需求、任务和材料，提交处理结果。
- 平台运营人员：管理企业、项目、服务商、场景可见范围和运营数据。

### 4.3 权限原则

- 组织决定默认数据边界。
- 项目决定场景、规则、数据源和服务商范围。
- 角色决定可见和可操作的业务对象。
- 任务负责人决定具体处理权限。
- 关键确认、审批、复核和归档动作必须记录操作者和时间。

## 5. 产品架构

产品架构图采用五层结构：

```text
用户与端
    ↓
业务入口
    ↓
业务对象
    ↓
业务处理
    ↓
业务沉淀
```

### 5.1 用户与端

- 企业用户。
- 平台运营方。
- 服务商。
- Web 企业工作台。
- Web 平台运营工作台。
- 微信小程序。

### 5.2 业务入口

- 做好一个商品。
- 找到一个客户。
- 完成一次合规处理。
- 做一份报价。
- 管理一次履约。
- 查看经营情况。

首页以场景导航为主，以任务中心为辅。企业用户打开系统时先选择业务目标；任务中心承接待处理、待确认、风险预警、待跟进和最近完成事项。

### 5.3 业务对象

- 企业、用户、联系人和项目。
- 商品、SKU、属性、素材、商品版本和渠道发布记录。
- 客户、采购商、供应商、服务商和联系人。
- 线索、客户画像、触达任务、跟进记录和商机。
- 询价需求、商品匹配、服务需求、物流报价和报价单。
- 合规案件、风险项、整改任务、合规材料、报关单和退税资料。
- 订单、履约单、履约节点、库存、入库记录和风险事件。
- 报告、数据任务、规则配置、通知和审计日志。

### 5.4 业务处理

- 信息采集和完善。
- 内容和材料处理。
- 语义搜索、筛选和匹配。
- 画像、评分和推荐。
- 风险识别和规则检查。
- 任务分配、审批和复核。
- 触达、报价、发布和协同。

### 5.5 业务沉淀

- 正式业务数据。
- 候选结果和确认记录。
- 商品、客户、报价和报告版本。
- 任务、通知和风险事件。
- 文件、图片、视频和业务材料。
- 操作日志、接口记录和审计记录。

## 6. 场景统一处理框架

所有场景使用以下统一定义，不要求页面完全相同，但要求业务契约完整：

```text
场景说明
→ 选择或创建业务对象
→ 填写、上传或选择输入
→ 处理进度
→ 候选结果
→ 确认、修改或驳回
→ 写回正式业务数据
→ 产生任务、通知或下一步动作
→ 历史记录与异常恢复
```

每个场景必须说明：

- 场景名称和解决的问题。
- 适用角色、企业和项目。
- 关联业务对象。
- 前置条件和输入材料。
- 处理步骤和人工确认点。
- 结果及其数据写入位置。
- 状态、任务、通知和后续场景。
- 失败、驳回、补充和重试方式。
- Web 入口和小程序入口。

## 7. 五条完整 Demo 闭环

### 7.1 商品经营

```text
小程序拍摄或上传商品
→ 创建商品草稿
→ Web 完善商品信息
→ 制作图片和视频
→ 完善多语言内容
→ 商品合规检查
→ 确认正式商品版本
→ 创建发布任务或完成发布
→ 小程序查看结果
```

起点：小程序创建商品草稿。

终点：商品形成正式版本，发布任务已创建或商品已发布。

主要对象：商品、SKU、商品素材、商品内容版本、合规记录、发布记录、场景处理记录和任务。

商品自身生命周期状态：

```text
草稿 → 待完善 → 可经营 → 需整改 → 已停用
```

商品工作台的内容、合规和发布进度由商品自身状态，以及关联的场景处理记录、合规案件和渠道发布记录汇总展示，例如内容处理中、待合规检查、待发布和已发布。这些是处理进度或渠道状态，不是商品主数据生命周期状态。处理结果必须先是候选图片、候选视频或候选描述，确认后进入素材库、商品版本或渠道版本。存在未处理风险时，商品进入“需整改”，不得进入正常发布状态。

### 7.2 线索经营

```text
选择目标市场、行业或商品
→ 发现采购商候选
→ 筛选和去重
→ 查看采购商画像
→ 确认并入库
→ 分配负责人
→ 发起触达
→ 记录跟进
→ 转为商机
```

主要对象：线索、采购商、企业、联系人、客户档案、客户画像、触达任务、跟进记录和商机。

线索主状态：

```text
待筛选 → 处理中 → 待确认 → 已入库 → 已分配 → 已触达 → 跟进中 → 转为商机
```

其他结果：无效线索、重复线索、暂不跟进、已转客户。

候选采购商未确认前只能作为候选线索。去重和合并必须保留来源与操作记录。采购商画像属于客户档案的可更新版本，不是一次性名单文件。

### 7.3 合规处理

```text
从企业、商品或订单进入
→ 选择境内或境外处理范围
→ 创建合规案件
→ 提交材料
→ 诊断和规则检查
→ 生成风险项
→ 生成整改任务
→ 补充材料或服务商协作
→ 复核
→ 通过或归档
```

主要对象：合规案件、风险项、整改任务、合规材料、规则版本、服务商、复核记录和审计记录。

案件主状态：

```text
待受理 → 处理中 → 待补充材料 → 待整改 → 待复核 → 已通过 → 已归档
```

境内和境外是同一合规处理结构下的不同处理范围，可以分别配置规则、检查项、接口和服务商。产品层不要求用户理解底层调用对象，技术层必须保持范围可区分。

合规完成的依据是风险项、材料、整改任务和复核结果，而不是诊断报告本身。

### 7.4 询价与报价

```text
从客户、商品或询价入口发起
→ 提交或上传询价需求
→ 确认需求信息
→ 匹配商品和服务
→ 比较物流方案
→ 组合报价方案
→ 生成报价版本
→ 发送给客户
→ 接受、拒绝、议价或转为跟进
→ 转为商机或订单
```

主要对象：询价需求、商品匹配、服务需求、物流报价、报价单、报价版本、客户反馈、商机和订单。

报价单主状态：

```text
草稿 → 待确认 → 已发送 → 客户已查看 → 议价中 → 已接受 / 已拒绝 / 已过期
```

报价修改产生新版本，旧版本只读保留。客户接受后可以转商机或订单；客户暂未决定则生成 CRM 跟进任务。

### 7.5 订单与履约

```text
客户接受报价或人工创建订单
→ 确认客户、商品、价格和交付要求
→ 创建订单
→ 建立履约节点
→ 跟踪备货、物流、报关、退税和交付
→ 发现风险并创建处理任务
→ 协同供应商或服务商
→ 更新库存和入库
→ 完成履约
```

主要对象：订单、履约单、履约节点、物流记录、通关记录、退税记录、库存、入库记录、风险事件、任务和文件。

订单主状态：

```text
草稿 → 待确认 → 已确认 → 执行中 → 部分完成 → 已完成
```

特殊结果：待补充信息、已暂停、已取消、履约异常。

风险事件必须关联订单和具体履约节点，并产生责任人任务。库存不足可以产生补货建议，补货和入库结果写回库存数据后继续履约。

## 13. 状态与异常规则

### 13.1 通用场景处理状态

```text
未开始 → 处理中 → 待确认 → 已确认
```

可转为：

```text
处理中 → 处理失败 → 重新处理
待确认 → 已驳回 → 重新处理
待确认 → 待补充 → 补充后继续
```

### 13.2 写回规则

- 处理中的中间结果不可视为正式业务数据。
- 候选结果可查看、比较、修改和驳回。
- 确认动作必须校验当前版本，避免覆盖他人已确认的更新。
- 写回成功后生成版本和审计记录。
- 写回失败时保留候选结果，显示可重试任务，不丢失用户输入。

### 13.3 异常恢复

- 外部连接失败：保留请求记录，按配置重试，超过次数后生成异常任务。
- 文件处理失败：保留原文件，允许重新提交或更换文件。
- 规则无法判断：标记为需人工判断，不自动通过。
- 权限变化：已创建的处理记录保留，后续动作按最新权限校验。
- 并发更新：提示用户刷新或基于新版本重新确认，不静默覆盖。
- 超时：处理记录进入超时状态并通知负责人。

## 17. 执行级补充约束

本节把前述产品原则补充为前端、后端和测试可以直接使用的约束。它不新增场景，只定义状态、权限、写回、跨端和第一阶段模拟边界。

### 17.1 状态机约定

所有状态变更必须由一个明确事件触发，并记录操作者、时间、来源端、前置状态和结果。后端负责校验允许的转换，前端只展示当前状态允许的操作。下方 17.9 的生命周期矩阵是唯一权威状态定义；本节的五行表只说明五条主流程的业务主线，不再单独定义可实现的完整状态集合。

| 流程 | 主要状态 | 触发事件 | 主要操作者 | 状态变更后的副作用 |
|---|---|---|---|---|
| 商品经营 | 草稿 → 待完善 → 待合规检查 → 待发布 → 已发布 | 创建草稿、完善确认、合规通过、发布完成 | 发起人、商品运营、合规人员 | 建立任务、生成版本、写入发布记录 |
| 线索经营 | 待筛选 → 待确认 → 已入库 → 已触达 → 跟进中 → 转为商机 | 完成筛选、确认入库、发送触达、记录反馈、创建商机 | 获客人员、销售人员 | 去重合并、建立客户档案、创建触达或跟进任务 |
| 合规处理 | 待受理 → 处理中 → 待整改 → 待复核 → 已通过 → 已归档 | 受理、提交诊断、确认风险、提交整改、复核通过、归档 | 合规人员、企业负责人、服务商 | 生成风险项、整改任务、通知和审计记录 |
| 询价报价 | 草稿 → 待确认 → 已发送 → 议价中 → 已接受/已拒绝/已过期 | 保存需求、确认报价、发送报价、客户反馈、有效期到期 | 销售人员、企业负责人、客户或内部代录人员 | 创建报价版本、触达记录、跟进任务、商机或订单 |
| 订单履约 | 草稿 → 待确认 → 已确认 → 执行中 → 部分完成 → 已完成 | 创建、确认、开始执行、节点完成、全部节点完成 | 订单负责人、供应商、服务商、平台运营 | 建立履约节点、风险事件、库存变化和通知 |

通用状态动作规则：

- 创建、提交、确认、驳回、补充、转派、暂停、恢复、取消、完成和归档都必须是有记录的业务事件。
- 已完成或已归档的对象不能直接编辑；需要重新处理时创建新版本或重新打开记录，并保留原记录。
- 任何状态变更失败时，主数据保持变更前状态，失败原因进入处理记录或异常任务。
- “部分完成”只用于确实存在多个可独立完成子项的对象，例如履约节点和批量商品处理。
- 过期、拒绝、取消和暂停不是删除；它们保留对象及历史，并定义可否重新打开。

### 17.2 候选结果写回协议

候选结果必须至少保存以下信息：

- `scene_run_id`：来源场景处理记录。
- `target_object_type` 和 `target_object_id`：目标业务对象。
- `source_version`：生成候选结果时读取的正式版本。
- `field_mapping`：候选字段写入正式对象的字段映射。
- `candidate_version`：候选结果版本。
- `status`：待确认、已确认、已驳回、已过期或写回失败。
- `idempotency_key`：同一处理请求的幂等标识。
- `confirmed_by`、`confirmed_at`：确认人和确认时间。

确认写回规则：

1. 确认时校验正式对象版本仍等于 `source_version`。
2. 版本不一致时不得静默覆盖，提示用户基于最新版本重新比较和确认。
3. 单一业务对象内的字段写回与新版本记录必须在同一事务边界内完成。
4. 跨业务对象副作用，例如写回商品后创建发布任务，先完成主对象写回，再以事件或任务方式创建下游动作。
5. 下游任务创建失败不能回滚已确认的主数据；系统保留事件和异常任务，支持幂等重试。
6. 批量处理允许部分成功，但每一条对象都必须有独立结果、错误原因和重试入口。
7. 自动写回只能由平台运营方在项目或场景配置中开启，并限定适用对象、字段、风险级别和版本策略；自动写回同样生成版本和审计记录。

### 17.3 权限矩阵

下表是第一阶段必须表达的最小权限边界。对象级权限按企业和项目作用域执行，任务负责人权限不能突破组织边界。

| 角色 | 查看本企业数据 | 新建/编辑本企业对象 | 确认正式结果 | 分配和转派任务 | 查看跨企业数据 | 管理项目和规则 |
|---|---:|---:|---:|---:|---:|---:|
| 企业负责人 | 是 | 是 | 是 | 是 | 否 | 否 |
| 商品/销售/履约人员 | 是 | 按职责 | 按场景授权 | 被授权时 | 否 | 否 |
| 合规人员 | 是 | 合规范围内 | 合规范围内 | 是 | 仅受授权案件 | 否 |
| 服务商 | 仅受分配对象 | 仅受分配对象 | 提交处理结果，不确认企业正式主数据 | 否 | 否 | 否 |
| 平台运营人员 | 受项目授权 | 受项目授权 | 按项目授权 | 是 | 受项目授权 | 是 |

权限实现要求：

- 每个业务对象带有组织归属，项目成员关系决定项目范围，任务负责人决定处理范围。
- 平台运营人员默认看不到企业全部敏感数据，只能看到项目授权范围。
- 服务商只能查看被分配的服务需求、案件、材料和任务；完成后提交结果，由企业或授权人员确认写回。
- 权限撤销后不能继续新建或修改，但已存在的记录和审计日志必须保留；待处理任务转为待重新分配。
- 详情页、列表页、下载文件和接口都执行同一套权限校验，不能只在前端隐藏按钮。

### 17.4 Web 与小程序一致性

- 业务主数据和状态以后端为唯一权威来源；两端不各自维护状态。
- 所有写操作返回对象最新版本、状态、处理记录摘要和下一步任务。
- 小程序提交后，Web 在下一次读取时必须看到相同状态；原型中用统一模拟数据源表现这一点。
- 采用对象版本号进行乐观并发控制。版本冲突时要求刷新、比较和重新确认。
- 文件上传先记录上传中、成功或失败状态；失败文件不能被当作已提交材料。
- 通知使用业务事件和幂等键去重，同一事件不因 Web 和小程序同时打开而重复创建任务。
- 五条流程都在原型中表现跨端状态同步；商品经营展示完整“小程序发起、Web 处理、小程序查看”，其他四条至少展示一个跨端待办或结果确认节点。

### 17.5 报价客户反馈边界

第一阶段不建设独立客户门户。报价发送后，原型由内部销售人员模拟“已发送、客户查看、客户反馈”，并将反馈写入报价和跟进记录。

第二阶段通过消息、邮件、分享链接或外部系统适配器接收真实反馈。外部客户身份、授权方式和回传事件由具体渠道适配器定义，不能让报价领域直接依赖某一个渠道。内部代录和外部回传使用同一组状态事件和审计记录。

### 17.6 第一阶段深度与模拟边界

| 交付类型 | 页面深度 | 必须可演示 | 模拟边界 |
|---|---|---|---|
| 商品经营 | 完整跨端纵向样板 | 草稿、候选结果、确认、写回、版本、发布任务、异常恢复 | 图片/视频处理、合规检查和发布使用模拟服务 |
| 线索经营 | 关键路径可走通 | 发现、筛选、去重、画像、入库、分配、触达、跟进、商机 | 线索数据源和发送渠道使用固定示例数据 |

### 17.8 架构边界补充

业务领域服务对自己的主数据负责，不能由其他领域直接修改其数据库表。跨领域变化通过明确的业务接口或事件完成：

```text
商品领域拥有商品、SKU、素材和版本
客户领域拥有客户、线索、画像和跟进
合规领域拥有案件、风险项、整改和材料
交易领域拥有询价、匹配和报价版本
订单与履约领域拥有订单和履约；库存与供应链领域拥有库存和入库
流程层拥有场景处理记录、任务、通知和运行状态
```

例如合规检查需要读取商品信息时，通过商品领域的查询接口获得；合规通过后，由合规领域发布“合规通过”业务事件，商品领域决定是否允许更新商品发布状态。这样既能复用场景，又不会形成跨模块直接写表。

### 17.9 权威对象生命周期与业务域归属

本矩阵是第一阶段原型、第二阶段接口和测试的共同状态契约。状态名称、触发事件和完成副作用以本表为准；“结束”表示当前处理完成，但不表示对象物理删除。

| 对象 | 负责业务域 | 权威状态 | 关键触发与结果 |
|---|---|---|---|
| Organization、User、Role、ProjectMembership | 企业与组织 | 启用、停用 | 创建并授权；停用后禁止新操作，历史记录保留 |
| PartyCompany、Contact | 企业与组织 | 草稿、有效、停用、合并 | 建档、核验、停用或合并；合并保留来源和目标关系 |
| CustomerRelation、SupplierRelation、ProviderRelation | 客户与线索 / 服务与物流 | 待确认、有效、暂停、结束 | 确认业务关系、暂停或结束；不复制基础企业档案 |
| Product | 商品与内容 | 草稿、待完善、可经营、需整改、已停用 | 创建、完善确认、合规不通过、停用；状态决定可否进入发布 |
| SKU、ProductAttribute | 商品与内容 | 草稿、待确认、有效、停用 | 商品确认时写入；商品停用时不可新增业务使用 |
| ProductAsset | 商品与内容 | 上传中、待确认、已确认、已驳回、失效 | 上传、处理完成、用户确认或替换；确认后关联商品版本 |
| ProductVersion | 商品与内容 | 编辑中、待确认、已生效、已废弃 | 基于正式版本产生；确认后成为当前版本，旧版本只读 |
| ChannelListing | 商品与内容 | 待发布、发布中、已发布、发布失败、已下架 | 创建发布任务、回传结果或重试；失败不改变商品正式版本 |
| Lead | 客户与线索 | 待筛选、处理中、待确认、已入库、已分配、已触达、跟进中、无效、重复、暂不跟进 | 筛选确认、去重、入库、分配和触达；入库后可建立客户关系 |
| CustomerProfile | 客户与线索 | 待生成、待确认、有效、已更新、失效 | 基于客户档案产生候选画像；确认后形成版本 |
| TouchTask | 客户与线索 | 待执行、执行中、已发送、失败、已取消 | 执行或取消触达；结果写入触达记录并更新线索/客户状态 |
| FollowUp | 客户与线索 | 待跟进、跟进中、已完成、已取消 | 记录沟通和下一步；完成可创建商机或新任务 |
| Opportunity | 客户与线索 | 新建、跟进中、报价中、已赢单、已输单、已关闭 | 线索或报价转入；赢单可请求创建订单 |
| Inquiry | 询价与报价 | 草稿、待确认、处理中、待补充、已确认、已关闭 | 提交、解析、补充和确认；确认后允许匹配和报价 |
| MatchResult | 询价与报价 | 处理中、待选择、已选择、已驳回、失效 | 产生候选商品/服务方案；选择后进入报价，不直接覆盖主数据 |
| ServiceRequest | 服务与物流 | 草稿、待受理、匹配中、待选择、已承接、已完成、已取消 | 识别需求、匹配服务商、承接或取消；承接产生服务任务 |
| LogisticsQuote | 服务与物流 | 待询价、处理中、待选择、已选择、已过期、失败 | 询价、返回方案、选择或过期；选择结果进入报价版本 |
| Quotation、QuotationVersion | 询价与报价 | 报价单：草稿、待确认、已发送、客户已查看、议价中、已接受、已拒绝、已过期；版本：编辑中、已生效、已废弃 | 确认、发送、客户查看、客户反馈或到期；接受可转商机/订单，修改产生新版本 |
| ComplianceCase | 合规与通关 | 待受理、处理中、待补充材料、待整改、待复核、已通过、已归档、已关闭 | 受理、诊断、补充、整改、复核和归档；通过产生合规通过事件 |
| RiskItem | 合规与通关 | 待确认、已确认、整改中、待复核、已解除、已豁免、已关闭 | 识别、确认、整改、复核或豁免；未解除风险阻止相关正式动作 |
| RectificationTask | 合规与通关 | 待处理、处理中、待提交、待复核、已通过、已退回、已取消 | 分配、提交、复核、退回或取消；通过更新对应风险项 |
| ComplianceMaterial | 合规与通关 | 待上传、上传中、已提交、识别失败、待补充、已确认、已作废 | 上传、提交、失败重传、确认或作废；已确认材料进入案件证据链 |
| ReviewRecord | 合规与通关 | 待复核、通过、退回、已撤回 | 复核风险项、整改或案件；退回必须产生补充/整改任务 |
| Order | 订单与履约 | 草稿、待确认、待补充信息、已确认、执行中、部分完成、已完成、已暂停、已取消、履约异常 | 确认、开始、节点更新、暂停、取消或完成；完成汇总履约结果 |
| FulfillmentNode | 订单与履约 | 未开始、处理中、待确认、已完成、存在风险、已暂停、已取消 | 开始、提交节点证据、确认、发现风险或解除风险 |
| RiskEvent | 订单与履约 | 新建、处理中、待复核、已解除、已接受、已关闭 | 发现、分配、处理、复核或接受风险；关联订单和履约节点 |
| Inventory、InboundRecord | 库存与供应链 | 库存：可用、预警、冻结、盘点中；入库：待入库、验收中、部分入库、已入库、异常 | 入库和质检更新库存；库存不足可创建补货任务 |
| Report | 经营分析与报告 | 生成中、待确认、已发布、已废弃、失败 | 生成候选报告、确认发布或重试；发布版本只读 |
| DataTask | 数据与分析支撑 | 待处理、处理中、部分完成、已完成、失败、已取消 | 启动、分批处理、完成或重试；每条数据保留结果和错误 |
| RuleConfiguration | 项目与规则配置 | 草稿、待发布、已生效、已停用、已过期 | 配置、审核、发布、停用或到期；案件记录保存使用的规则版本 |
| SceneRun | 流程运行 | 未开始、处理中、待确认、待补充、已确认、已驳回、失败、超时、已取消 | 启动、处理、确认、补充、驳回、重试或取消；关联候选结果和任务 |
| CandidateResult | 流程运行 | 生成中、待确认、已确认、已驳回、已过期、写回失败 | 产生、确认、驳回、过期或写回失败；确认写回正式对象并生成版本 |
| Task | 流程运行 | 待处理、处理中、待确认、待复核、已完成、已退回、已取消、已超时 | 分配、领取、提交、复核、退回、完成或超时；操作必须留痕 |
| Notification | 流程运行 | 待发送、已发送、发送失败、已读、已失效 | 业务事件触发，发送去重；失败产生可重试记录 |
| FileAsset | 文件与素材支撑 | 待上传、上传中、已上传、处理中、可用、失败、已作废 | 上传、处理、失败重传或作废；业务对象只能引用可用文件 |
| AuditLog | 审计支撑 | 已记录、归档 | 关键动作写入后不可修改；归档不影响查询 |
| IntegrationRecord | 外部连接支撑 | 待发送、处理中、成功、部分成功、失败、待重试、已放弃 | 请求、回调、重试或放弃；保存幂等键和响应摘要 |

归属补充规则：

- `PartyCompany` 是企业、采购商、供应商和服务商的共同基础档案；企业、客户、供应商和服务商在产品上是业务身份或关系，不复制成四套企业主表。`CustomerRelation`、`SupplierRelation` 和 `ProviderRelation` 保存对应业务关系。
- `ServiceRequest` 和 `LogisticsQuote` 由服务与物流域负责；交易域通过接口读取候选结果并引用已选择方案。
- `Report` 和 `DataTask` 由经营分析与数据支撑域负责；报告读取各业务域的授权数据，但不反向直接修改业务主数据。
- `RuleConfiguration` 由项目与规则配置域负责；合规域、商品域和履约域只能读取已生效版本，并在处理记录中保存版本号。
- `IntegrationRecord` 由外部连接支撑域负责；业务域只接收成功、失败或部分成功事件，不直接持有第三方调用细节。
- `SceneRun`、`CandidateResult`、`Task` 和 `Notification` 由流程运行域负责；业务域拥有正式业务对象及其业务状态。

### 17.10 状态矩阵与五条主流程的引用关系

五条主流程中的简化状态必须映射到 17.9 的对象状态，不允许另建一套状态：

```text
商品经营：SceneRun + Product + ProductAsset + ProductVersion + ComplianceCase + ChannelListing；商品工作台显示的内容、合规和发布进度由这些关联对象汇总，Product 自身只使用其生命周期状态。
线索经营：SceneRun + Lead + CustomerProfile + TouchTask + FollowUp + Opportunity
合规处理：SceneRun + ComplianceCase + RiskItem + RectificationTask + ComplianceMaterial + ReviewRecord
询价报价：SceneRun + Inquiry + MatchResult + ServiceRequest + LogisticsQuote + Quotation + QuotationVersion + Opportunity；客户已查看是 Quotation 的正式状态，由外部回传或内部代录事件触发。
订单履约：SceneRun + Order + FulfillmentNode + RiskEvent + Inventory + InboundRecord
```

前端页面根据对象状态显示操作，后端根据同一矩阵拒绝非法转换，测试以“当前状态 + 触发事件 + 操作者 + 前置条件 + 后置副作用”为最小测试单元。
